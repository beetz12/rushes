# Windows native encoder admission experiment

The unconditional cohort trial failed the full Mac gate: composed media was about427ms shorter than the unchanged recording duration check. A fresh same-profile old-code gate passed. Both results remain evidence; neither identifies a unique cause. Apply the cohort only as a Windows-specific experiment, not a verified repair. One raw VP8 encoder at the screen's 4 Mb/s rate succeeds, while the larger graph can miss native Start. The one-encoder result rules out bitrate alone. It does not establish a hardware limit, buffer cause or unsupported browser.

Read the browser’s low-entropy UAData platform once for this start. Only its Windows value selects the cohort; when that field is unavailable, legacy Win32 is the fallback. Mac and missing, unknown or other values retain parallel native admission. This reported hint can be overridden and is not a security identity. Record the selected policy and bounded platform through the existing manifest event channel before draft creation. Do not select by test, workflow, source mode or timing outcome.

On Windows, open the existing native recorders in two cohorts. The first contains the first slot marked as video by our own record function, plus every audio-only slot. Issue their real Start calls, start the existing composition worker, then wait for their genuine active native Start events. Admit each remaining video slot separately: issue its real Start, await its active acknowledgement, then recheck take ownership before admitting the next. Recheck ownership after the final native join too. Audio-only tracks retain their initial admission instead of waiting behind every video encoder. Camera/composed native starts may move later; their real offsets remain recorded.

One deadline expires 10 seconds after the original startedAt, covering every cohort. Neither waiting nor a later call restarts it. A late callback cannot beat an expired deadline. Keep the existing codecs, rates, timeslice, source clocks, frame limits, byte bounds, pause mapping, playback checks, source/PCM qualification,100 ms sync and250 ms gap limits. Deferred heads must pass those same media checks; no synthetic leading data or clock shift is added.

Install event waiters before native calls and observe their combined rejection immediately. Retire the shared timer and temporary acknowledgement listeners when admission ends or fails. Retain actual native event counters separately. Inactive Start events synthesized during Stop cannot admit a cohort. Take ownership is checked at every native-call boundary. Stop, Cancel or source failure must prevent later native starts and preserve the existing terminal owner's cleanup and first failure.

Pause is still nonterminal. If the take becomes paused during admission, a later slot inherits pause in the same task as its native Start. Native Start in a paused but still owned recorder is active, while an inactive event is not. The common deadline still applies if pause delays an acknowledgement. This case needs explicit mocked coverage and actual media qualification; it is not a reason to extend startup.

Exact Chromium 155 sources show that MediaRecorder.start reaches the handler which constructs a VideoTrackRecorderImpl for each encoded video. Its pending-support path may hold capture buffers. This makes reduced simultaneous cold admission a plausible Windows experiment, not the observed failure cause. Forced software already failed in the full graph, so asynchronous hardware-support notification alone is insufficient. Native Start demonstrates a live event, not decoded completeness or complete factory readiness.

The alternative is a two-parallel-raw-encoder diagnostic, which isolates native concurrency with less product policy change. Prefer that control if cohort admission cannot preserve lifecycle or timing. This proposal earns no fix claim until independent review, the full source gate, same-source Mac parallel media checks and actual public Windows native/media/retirement results all pass. No hosted backend or private Actions change is involved.

This design uses our current coordinator, permitted plan/design notes, measured generated test metadata and official BSD Chromium API behavior. No third-party recorder implementation is copied and no forbidden source was opened.


## Serial remaining-video comparison

The current Windows delivery arms use the ordinary encoder policy and observed live screen, microphone and tab-audio acknowledgements. A later camera or composed acknowledgement still failed at the shared deadline; one arm reached camera as well. Those bodies did not return a policy manifest or native call timestamps, so ordering is tied to the exact source path rather than independently timed call probes. The first-group events are progress, not playable media.

Keep the observation-only C4 baseline separate. Change only dispatch of remaining video slots for C5. The first group and early audio stay unchanged; Mac and unknown platforms already admit every slot in parallel, leaving no later sequence there. Do not reset the common ten-second expiry after a middle acknowledgement. A missing or inactive middle acknowledgement, Stop, Cancel or source failure must prevent the next native call. All real start-event offsets and the original head/body/tail, source/PCM, sync and byte predicates remain unchanged. No offset correction, padded samples, new telemetry, flags, retry or sleep is introduced.

Start admission and cleanup remain separate questions. Hold the actual Stop events for each issued slot in lifecycle tests and require their release before startup rejection settles. Never request or count Stop for a slot that was not started. These controlled event tests do not prove owned-process retirement. Actual Windows native/media and independent cleanup must still pass; if startup fails again, preserve it and use the earned two/three-raw alternative or scoped ownership evidence instead of rerunning an unchanged candidate.
