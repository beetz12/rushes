## What it does

Cap is the most complete open-source Loom alternative I have seen. A desktop app records a display, a window, an area or the camera alone, together with a microphone and optionally system audio and a floating camera bubble. It offers two recording modes. The fast mode reserves a share link before capture begins and uploads while you record; on stop it copies the link to the clipboard and opens the share page, which can already play what was uploaded. The studio mode records each source to its own local file, then opens a full editor with backgrounds, padding, rounded frames, click-driven zoom, cursor smoothing, masks, text, scene layouts, captions and trimming, and exports MP4, GIF or ProRes MOV or uploads the result.

The web side is a complete hosted product: share pages with an HLS or MP4 player, timestamped comments (text, emoji reactions, voice notes and video replies), transcripts, AI titles, summaries and chapters, view analytics, password protection, custom domains, organisations and spaces, Loom import, a transcript-driven cut editor, and a server-side GPU render farm for studio exports. Storage can be Cap's cloud, a user's own S3-compatible bucket, Google Drive, or a fully self-hosted stack started with Docker Compose.

For automation it ships a command-line tool that shares the desktop app's binary, prints JSON for every command, streams newline-delimited JSON events while recording or exporting, exposes a local MCP server, and installs an agent skill. A deep-link scheme can start, stop, pause and resume recordings from other apps.

## Feature inventory

- **capture-screen (5).** ScreenCaptureKit on macOS with window exclusion (the app's own control bar, and the camera bubble in studio mode), crop for area capture, and a hidden system cursor when the app draws its own cursor later. Windows Graphics Capture on a D3D11 device, with a cadence limiter that only decimates when a high-refresh monitor delivers measurably faster than the target rate. Linux X11 and PipeWire portal capture. Output size is clamped to H.264 limits and to even dimensions. Display notch geometry is recorded so the editor can draw around it.
- **capture-camera (5).** A camera feed actor shared by the preview bubble and the recorder. On macOS it pins the device format and its minimum frame duration so the camera cannot free-run at a higher rate than the pipeline assumes. Cameras are identified by a USB vendor and product id parsed from the platform id, so the same camera is found again after a reconnect. Studio mode writes the camera to its own file.
- **capture-audio (4).** Microphone through a patched cpal; system audio through ScreenCaptureKit audio (macOS 13 and later) or WASAPI loopback on Windows. In studio mode mic and system audio are separate tracks; in instant mode they are mixed into one track. A 48 kHz audio-sample clock drives timing, with smoothing of noisy capture timestamps. Voice isolation (RNNoise) and stereo handling exist in the editor. Known weakness: macOS system audio arrives roughly 85 to 190 ms late and is not compensated.
- **recording-controls (4).** Countdown with a start gate (pipelines warm up during the countdown and frames are discarded until the gate opens), a floating controls bar with live timer, pause and resume (each resume starts a new numbered segment), cancel, restart, global hotkeys, a tray menu, deep-link actions and CLI start/stop by recording id.
- **camera-overlay (4).** A borderless floating window with round, square or full-frame shapes, sizes from 150 to 600 points (default 230, presets 230 and 400), zero-copy preview from IOSurfaces, preview-only mirroring done in hardware, and background blur or removal through the MIT camera-effects crate. In studio mode the bubble is excluded from capture and recomposited in the editor; in instant mode it stays in the screen capture, burned in.
- **annotation (3).** The screenshot editor has arrows, circles, rectangles, text, blur masks and freehand drawing. The Chrome extension has a live drawing overlay. The desktop video editor has sensitive (blur) and highlight masks and text overlays with keyframes. I found no live on-screen drawing during desktop video recording.
- **compositing-render (5).** A wgpu renderer with separate layers for background (colour, gradient, animated gradient, image, blur), the display, the camera (including a 3D-tilted camera card), the cursor (smoothed, with click ripples and custom cursor images), keyboard-press overlays, captions, text, masks, colour grading, transitions and a watermark, all as WGSL shaders. Zoom and screen movement use spring-mass-damper motion. Export renders straight to NV12 on the GPU to feed the encoder.
- **editing (5).** A timeline of clips that point into recording segments with a range and speed (with options for audio during speed changes), per-clip volume, clip transitions, zoom ranges (manual or auto from clicks), mask ranges, text ranges, scene ranges (camera only, hide camera, split screen, floating split cards), style overrides, image overlays, captions and keyboard tracks. A separate web editor lets a viewer cut the video by deleting transcript words, including one-click removal of filler words.
- **transcription-captions (5).** Local captions with whisper and NVIDIA Parakeet models (Parakeet not on Intel Macs), downloaded on demand into an app data folder, with word timestamps. On the server, AssemblyAI produces the canonical transcript; for instant recordings a live transcription workflow transcribes audio segments as they upload and the share page shows live captions before the recording ends.
- **ai-features (4).** Server-side titles, summaries and clickable chapters through a provider-selection layer over the Vercel AI SDK (several model families, configurable per deployment, with separate generation and chat model slots); an agent API and MCP server on the web side.
- **export-formats (4).** MP4 H.264 with four compression presets defined as bits per pixel (0.3, 0.15, 0.08, 0.04) with matching CRF values (24, 28, 32, 36) or a custom value, plus fps and resolution; GIF; MOV with ProRes. Server exports can be split across GPU workers that stream HLS while rendering.
- **project-format (4).** A project is a folder (shown as a `.cap` bundle) holding a recording metadata JSON, an edit-configuration JSON and a content tree of numbered segment folders. Each segment holds one file or fragment folder per source, plus cursor and keyboard event files. Every track records its own start time relative to a shared recording epoch and the capture device id. Strong, but it carries many legacy variants.
- **sharing-hosting (5).** Instant mode reserves a video id and link before recording, uploads each finished two-second segment with presigned PUTs, re-uploads a JSON manifest about once a second, then signals completion so a durable server workflow assembles the final MP4. Studio exports upload as files or multipart. Custom S3 buckets, custom domains, passwords and organisation sharing exist.
- **viewer-web (5).** The share page plays a live HLS stream built on the fly from the uploaded manifest while recording continues, with an in-progress overlay, then swaps to the processed MP4. It has timestamped threaded comments (text, emoji, voice, video), a waveform and filmstrip timeline, transcript and summary tabs with chapters, caption tracks, downloads, call-to-action overlays, and owner analytics.
- **teleprompter-scripts (3).** A floating teleprompter window that stays above other apps on every Space, default 560 by 320, with play/pause, words-per-minute scrolling, opacity and font size. Basic but present.
- **platform-packaging (4).** macOS bundle with camera and microphone usage strings, Windows packaging, Linux AppImage, deb and rpm; an in-app updater with stable and nightly channels; the CLI is installed as a shim pointing at the app's own binary.
- **performance-reliability (5).** Crash-safe fragmented recording, a recovery scan on launch, atomic manifests, per-pipeline health events and drop-rate monitoring, disk-space callbacks that stop the recording and keep the files when storage runs low, an optional out-of-process muxer, a load-time repair for tracks stamped at the wrong frame rate, upload resume and SHA-256 upload verification, and a large set of benchmark and stress examples.
- **extensibility-automation (5).** JSON CLI with NDJSON event streams and a machine-readable command guide, a local MCP server and agent skill, deep-link actions, user automation rules (save copy, webhook) after screenshot, record or upload, recorder and embed SDK packages, and a web agent API with idempotency keys and OAuth for MCP clients.
- **privacy-security (4).** Permission checks that never trigger prompts, password-protected shares, encrypted storage of users' own S3 credentials, a log scrubber that strips presigned-URL credentials before diagnostic upload, private viewer grants, and full self-hosting. Weak points: default secrets in the compose file and analytics that rely on a third-party service and host-provided geo headers.

## Architecture

**Process model.** The desktop app is a single native Rust process (gpui) that owns windows (main, controls bar, camera bubble, editor, teleprompter, settings, target overlays), long-lived device feeds (camera and microphone actors that previews and recordings share), and recording actors. Recording runs inside an actor per session; each source gets its own output pipeline (source to encoder to muxer) on its own threads, and every pipeline reports health events up to the actor. An optional out-of-process muxer moves the muxing step into a child process that receives encoded packets over its stdin using a small framed binary protocol with a magic number, version, kind byte and CRC, and is respawned if it dies (`crates/recording/src/output_pipeline/oop_muxer.rs`, `crates/cap-muxer-protocol/src/lib.rs`). It is off by default.

**Studio capture and files.** For each segment (a new one after every resume) the recorder creates one pipeline per source. On macOS with crash recovery on and no camera, the screen goes through FFmpeg's DASH muxer into a folder of an init segment plus two-second fragmented MP4 media segments, encoded by VideoToolbox fed directly from capture IOSurfaces, with software x264 as the fallback. Without fragmenting, the screen goes to an AVFoundation asset writer MP4. The camera goes to its own MP4 (or its own fragment folder), the microphone to Ogg Opus (or fragmented AAC), system audio to its own Ogg or fragmented AAC, and cursor moves, clicks, cursor images and key presses to JSON and binary sidecars, written incrementally when fragmenting. Cursor images are deduplicated across segments in a shared cursors folder. System audio is anchored at the recording epoch rather than its first packet, because loopback capture only delivers while something plays and a late first packet would otherwise cut the head off the other tracks (`crates/recording/src/studio_recording.rs:3120-3520`).

Important caveat for David: on macOS the code turns fragmenting off for the whole segment whenever a camera is active, so the most common Loom case (screen plus camera) falls back to non-fragmented MP4 writers that are only playable once finalized (`crates/recording/src/studio_recording.rs:3138-3160`). I did not find the reason in the code.

**Encoding defaults.** Studio defaults to 60 fps, capped at 30 when a camera is active (and 24 in the low-memory compatibility profile), chosen automatically when the machine has under 16 GB of RAM. Instant mode defaults to 30 fps and caps output width at 1280 on the free plan and 1920 on paid plans. The FFmpeg path sizes bitrate as bits per pixel (0.3 quality, 1.0 ultra, 0.15 instant). The AVFoundation path targets roughly 10 Mbps for 1080p30 in the balanced profile, double that for ultra and half for compatibility, about 3.5 Mbps for an instant 1080p30 stream, and puts a keyframe every three-quarters of a second so the editor can seek quickly. On Windows the encoder order depends on GPU vendor (NVENC, AMF, QSV, Media Foundation) with x264 last (`crates/recording/src/defaults.rs`, `crates/enc-ffmpeg/src/video/h264.rs:60-80`, `crates/enc-avfoundation/src/mp4.rs:1080-1110`).

**A/V sync.** Timestamps carry a monotonic instant, wall time and the platform host clock (mach absolute time or the performance counter) so capture callbacks from different APIs map onto one timeline. All pipelines share one start time. A start gate holds every pipeline closed until the countdown ends; frames before the gate are dropped, so the first admitted frame of each source is time zero, with a 20-second failsafe that admits frames if nobody opens the gate. When segment start times are settled, a display start that differs from the camera's (or, without a camera, the mic's) by more than 30 ms is snapped to it. The metadata stores each track's start offset and the player trims to the latest start across tracks. Measured results in the crate's findings file: camera, mic and display within 0 ms of each other in tests, mic timing under 1 ms in fragmented mode, system audio still 84 ms or more late (`crates/recording/FINDINGS.md`, `crates/recording/src/output_pipeline/start_gate.rs`, `crates/timestamp/src/master_clock.rs`). The editor also reads a per camera-and-mic calibration store and applies a stored offset; the analyzer that would fill it (audio transients correlated with video motion peaks) exists, but I did not find the apps calling it.

**Crash recovery.** The fragment muxer rewrites a JSON manifest after every completed segment through write-temp, fsync, rename, fsync-directory, listing completed segments with durations and sizes, codec parameters and a completion flag (`crates/enc-ffmpeg/src/mux/segmented_stream.rs`). The recording metadata carries a status (in progress, needs remux, failed, complete). On launch the app scans the recordings folder, locks each project whose status is in progress or needs remux, keeps only fragments that are at least 100 bytes with a well-formed tail, concatenates fragments per track, merges, probes that the result decodes, writes a project configuration with a timeline, and publishes the result through a small journal so a crash during recovery cannot leave a half-replaced project (`crates/recording/src/recovery.rs`). A second repair runs when the editor opens: it detects camera or screen tracks whose duration is a multiple of the true span (a camera delivering 60 fps into a 30 fps pipeline, or a 165 Hz monitor on Windows) and rescales their timestamps losslessly, keeping a backup and refusing the result unless the healed duration lands within 5 percent of the expected span (`crates/recording/src/track_heal.rs`).

**Instant mode and upload during recording.** Before capture starts the app asks the server to create a video record and gets back an id; the share link is the server URL plus that id. The instant recorder writes screen video and a mixed audio track as two DASH fragment streams. Each time a segment completes, an event goes to an uploader task that prefetches presigned PUT URLs in batches of 20, uploads the init and media segments under a per-video prefix with three attempts each, and uploads an aggregate manifest at most once per second. At stop it uploads the final manifest marked complete and calls a completion endpoint. The server starts a durable workflow that asks the media worker to mux segments into an MP4, then transcribes and generates AI metadata. Upload state is persisted per project with a lock, so an interrupted upload can be resumed by rescanning the segment folders, and the server can return a verification receipt keyed on a SHA-256 of the manifest (`apps/desktop-gpui/src/upload.rs`, `crates/recording/src/upload_resume.rs`, `crates/recording/src/upload_verification.rs`, `apps/web/lib/desktop-segments-finalization.ts`).

**What the viewer gets first.** A playlist endpoint reads the uploaded manifest from the bucket and synthesizes a master playlist plus separate video and audio media playlists with fMP4 init maps and presigned segment URLs. While the manifest is incomplete the media playlists carry no end tag, so hls.js treats them as a live stream; once complete they become VOD playlists. The share page probes a status variant of the endpoint with backoff, shows a recording-in-progress overlay, overlays live captions from the live transcript, and swaps to the processed MP4 when the server finishes (`apps/web/app/api/playlist/route.ts:180-430`, `apps/web/app/s/[videoId]/_components/segment-playback-probe.ts`, `apps/web/app/s/[videoId]/_components/ShareVideo.tsx`).

**Web and self-hosting.** The compose file runs four long-lived containers: the Next.js web app (UI, API, auth, workflows), the media worker (FFmpeg probe, thumbnail, convert, edit, segment mux and recording verification, calling back to the web app through a signed webhook), MySQL 8, and MinIO, plus a one-shot job that creates the bucket. Auth is NextAuth with email magic links; without an email provider the login link is printed to the web container's logs. Users can attach their own S3-compatible bucket (AWS, R2, B2, MinIO, Wasabi); those credentials are stored encrypted with a database encryption key. Optional services: AssemblyAI for transcripts, an LLM provider for AI metadata, Resend for email, Tinybird for view analytics (events with session, browser, OS, device and geo, kept 90 days, geo taken from Vercel request headers). The desktop app points at a self-hosted server through a server-URL setting (`docker-compose.yml`, `packages/database/schema.ts:587-843`, `scripts/analytics/tinybird/datasources/analytics_events.datasource`).

**What the MIT crates give a new project.** These can be copied with the MIT notice:

- `cap-camera` (`crates/camera`): a cross-platform camera facade. `list_cameras()` returns `CameraInfo` values with a device id, display name and an optional `ModelID` (USB vendor and product id). `formats()` lists width, height and frame rate. `start_capturing_with_mode` takes a `CaptureMode` (`Native` pins the device format for zero conversion; `Compatibility` lets the OS negotiate for devices that stall) and a frame callback delivering `CapturedFrame` with a timestamp; the handle stops capture on drop. Backends: `cap-camera-avfoundation` on macOS, `cap-camera-windows` (Media Foundation with DirectShow fallback in `cap-camera-mediafoundation` and `cap-camera-directshow`), v4l on Linux. `cap-camera-ffmpeg` converts frames to FFmpeg frames.
- `cap-camera-effects`: GPU background blur and removal. On macOS it uses Apple Vision person segmentation; elsewhere an embedded ONNX selfie-segmentation model through ONNX Runtime (CoreML or DirectML execution providers), then a guided-filter matte, Gaussian blur and composite in WGSL. It has a global kill switch so a host can disable blur after a crash. The two `.onnx` files in its assets folder carry their own upstream licences, which I did not verify.
- `scap-screencapturekit`: a thin ScreenCaptureKit wrapper with a `Capturer` built by `CapturerBuilder` (sample-buffer and stopped-with-error callbacks), a `StreamCfgBuilder` (size, source rect, cursor, fps), `has_permission` and `request_permission`, and `is_system_audio_supported` (macOS 13 and later).
- `scap-targets`: display and window enumeration for macOS, Windows and Linux including Wayland: logical and physical sizes, refresh rate, notch geometry, the display under the cursor, the topmost window under the cursor, owner app name and icon, and window bounds relative to its display. This is what a capture-target picker needs.
- `scap-direct3d` (Windows Graphics Capture), `scap-cpal` (system-audio loopback through cpal, with a silence keep-alive) and `scap-ffmpeg` (converts ScreenCaptureKit, Direct3D and cpal frames into FFmpeg frames).

What they do not give: the pipelines, sync, start gate, fragmenting, recovery, cursor capture, rendering and upload are all AGPL. The MIT crates also depend on Cap-pinned git forks of cidre, cpal and rust-ffmpeg and on a generated workspace-hack crate, so lifting them means pinning those forks and removing the workspace-hack line.

**Verified versus assumed.** Verified by reading code: file layout, defaults, encoder order, manifest writing, recovery scan rules, start gate, instant upload flow, playlist synthesis, compose services, schema of comments and buckets, MIT crate APIs. Taken from repo docs rather than code: the A/V sync measurements (crate findings file) and the claim that the gpui app is what ships (agents file and gpui README). Not verified: whether the post-recording sync analyzer is wired in, the licences of the ONNX models, and why macOS disables fragmenting with a camera.

## Best ideas

1. **Crash-safe per-track fragments with an atomic manifest** (clean-room). Write every source as an init segment plus two-second fMP4 fragments, rewrite a small manifest after each fragment with temp file, fsync, rename and directory fsync, and on next launch rebuild any project whose status says unfinished from the fragments that pass a size and tail check. Matters most for David: a crash or power loss loses at most two seconds. Do it for the camera too, which Cap skips on macOS.
2. **Separate tracks per segment with per-track start offsets** (clean-room). One folder per pause-separated segment, one file per source (screen, camera, mic, system audio, cursor, keys), each with its own start time against one shared epoch and its device id. This matches David's editing tool, which already takes a screen file, a camera file and an offset.
3. **Warm-up start gate** (clean-room). Build sources, encoders and muxers during the countdown and drop all frames until the gate opens, so the first admitted frame of every source is time zero; add a failsafe that admits frames after a timeout. Instant start with no first-second desync.
4. **Two recording modes with different contracts** (idea-only). A quick mode that burns the bubble into the screen, mixes audio, caps resolution and frame rate, uses a low bitrate and uploads while recording; and a studio mode that keeps every source separate at higher quality for local editing.
5. **Upload fragments while recording** (clean-room). Reserve the share id and link before capture starts; upload each finished fragment by presigned PUT with batched URL prefetch and retries; re-upload a manifest about once a second; call a completion endpoint at stop so the server assembles the MP4.
6. **Live HLS synthesized from the manifest** (clean-room). The server builds HLS playlists from the uploaded manifest with no end tag until the recording completes, so a viewer can watch while the author is still recording, then the page swaps to the final MP4.
7. **Agent-first CLI** (idea-only). JSON on every command, newline-delimited JSON events for record and export, an explicit start/stop lifecycle keyed by recording id with a detach mode, a machine-readable command guide, a local MCP server, and reuse of the desktop login. Plus URL-scheme actions for start, stop, pause and resume.
8. **Non-prompting permission checks** (idea-only). Check screen recording, accessibility, camera and mic with preflight APIs that never prompt and never poll the shareable-content API (Cap documents a large memory leak from polling it). Separate a not-yet-asked state (show a grant button) from a denied state (deep-link to the right System Settings pane).
9. **Reuse the MIT camera crate** (copy-with-notice). Camera enumeration, stable vendor and product ids for reconnection, format listing and frame-duration pinning so a camera cannot silently deliver 60 fps into a 30 fps track.
10. **Reuse the MIT ScreenCaptureKit and target crates** (copy-with-notice). A ready capturer, stream config builder, permission helpers, and display and window enumeration with notch, refresh rate and window-under-cursor.
11. **Hardware-first encoder ladder with pixel-based bitrate** (clean-room). VideoToolbox fed with IOSurfaces directly, software fallback, bitrate scaled from pixel count and frame rate, and a short keyframe interval for fast editor seeking.
12. **Click-driven auto zoom** (clean-room). Turn each click into a zoom window from 0.3 s before to 2.5 s after, ignore clicks in the last second, end 0.8 s before the end, merge windows less than 2.5 s apart, zoom 2x, and follow the cursor with spring motion.
13. **Upload resume and verification** (clean-room). Persist upload identity per project behind a lock, rescan local fragments to resume after a crash or network loss, and treat the upload as done only after the server confirms a SHA-256 of the manifest.
14. **Load-time repair of wrongly stamped tracks** (clean-room). When a track's duration is a clean multiple of the real span, rescale its timestamps losslessly with a backup and a tolerance check.
15. **Local word-level captions** (idea-only). Download whisper or Parakeet models on demand and transcribe locally with word timestamps for captions and later transcript editing.
16. **Small self-host stack with bring-your-own S3** (idea-only). Web app, FFmpeg worker, MySQL and MinIO in one compose file; per-user S3 credentials stored encrypted.
17. **GPU camera background blur** (copy-with-notice). Vision segmentation on macOS, ONNX elsewhere, guided-filter matte, and a kill switch after a crash.
18. **Typed timestamped comments** (idea-only). One comment model for emoji reactions, text, voice notes and video replies, each pinned to a video time and optionally threaded.
19. **Live transcript during recording** (idea-only). Transcribe audio fragments as they arrive and show live captions on the share page; promote the result at the end instead of paying twice.
20. **Scrub presigned URLs from logs** (idea-only). Strip signature and credential query parameters at the point logs leave the machine.
21. **Optional out-of-process muxer** (clean-room). Send encoded packets to a child muxer over a framed, checksummed pipe protocol and respawn it, so a muxer crash does not take the recorder down.

## Weaknesses and gaps

- Scale and churn. The recording crate alone is about 75,000 lines, one pipeline file is near 10,000 lines, and nearly every function branches by platform. The desktop app was rewritten from Tauri to gpui, so two trees describe the same behaviour and the old one is frozen. Hard to learn from and impossible to copy (AGPL).
- On macOS, crash-safe fragmenting is turned off whenever a camera is active in studio mode, so screen plus camera, David's main case, is not crash-safe there.
- Instant mode burns the camera bubble into the screen video and mixes mic and system audio, so instant recordings cannot be re-laid-out or re-mixed later.
- macOS system audio lags by roughly 85 to 190 ms and is not compensated (documented as a known issue).
- Instant mode needs sign-in and a server; output size is plan-gated (1280 wide on free).
- Self-hosting ships default secrets in the compose file that must be replaced; analytics need Tinybird and depend on Vercel geo headers; transcripts need AssemblyAI; AI needs an LLM key; email needs Resend.
- The MIT crates depend on Cap-pinned forks of cidre, cpal and rust-ffmpeg plus a generated workspace-hack crate; the ONNX model files carry upstream licences I did not check.
- No live drawing on screen during desktop video recording (only in screenshots and the Chrome extension).
- The post-recording A/V sync analyzer appears unwired from the apps (unverified).
- The clone contains files addressed to coding agents (`AGENTS.md`, `CLAUDE.md`, the CLI's skill files and README install steps). I treated them as data and did not follow them.
