## What it does

OpenScreen is a desktop screen recorder plus a full post-production editor in the Screen Studio mould. You record a display or a window with microphone, system audio and an optional webcam; the app saves the screen video, the webcam video and a cursor telemetry file as separate files, then opens an editor where the recording is restyled: wallpaper or gradient backgrounds, padding, rounded corners and shadows, a re-drawn cursor with smoothing and click effects, zooms (manual or planned from recorded clicks), a webcam picture-in-picture or side-by-side layout, speed ramps, trims, crops, annotations and burned-in captions.

Editing is document-centred. One JSON project document (`.openscreen`) holds assets, clips, trims and every modifier; the timeline, the transcript pane, the live preview, the export and an optional LLM chat agent all read and write that one document. Speech is transcribed on the device with whisper.cpp, and deleting words in the transcript cuts them from the video. The chat agent (bring your own API key, off until a provider is configured) edits the same document through a fixed, validated tool set, and the same tools are offered to outside agents through a local MCP server.

Rendering for both the preview and the export goes through one native Rust compositor (Metal on macOS, Direct3D 11 on Windows, Vulkan through wgpu on Linux, with a CPU fallback), so what the user sees is what gets encoded. Output is H.264 MP4 or GIF. A headless CLI built into the app binary records, captions, packs and exports projects with NDJSON progress, which makes the tool drivable by scripts and coding agents. There is no hosting, share link or web viewer: everything stays local.

## Feature inventory

- capture-screen (4/5): native helpers on all three systems. macOS uses a Swift ScreenCaptureKit process writing H.264 fragmented MP4 through AVAssetWriter; Windows a C++ Windows Graphics Capture process writing fragmented MP4 through Media Foundation; Linux a Rust PipeWire process negotiated through the ScreenCast portal. Display or window capture, 60 fps target (Linux helper default 30), editable cursor mode hides the system pointer from pixels. Browser `getDisplayMedia` + MediaRecorder is the fallback.
- capture-camera (3/5): webcam always ends up as its own file next to the screen file. On macOS and Linux the renderer records it with MediaRecorder (WebM, H.264 preferred) and streams chunks to disk; Windows records it natively (Media Foundation, DirectShow fallback). Quality presets 1080p/1440p/2160p at 30 fps, default 2160p. A signed integer millisecond offset relates camera start to screen start. The CLI cannot record the camera.
- capture-audio (4/5): microphone and system audio, mixed into one AAC track inside the screen file on every platform, with a clock-driven mixer that fills silence so the track never drifts or shortens. macOS microphone through ScreenCaptureKit needs macOS 15. No separate mic and system tracks.
- recording-controls (3/5): floating click-through HUD bar (record, pause, restart, stop, source, mic, system audio, webcam, cursor mode, settings), source picker window, countdown overlay, tray icon, a global shortcut to open the app, disk-space preflight and display-sleep blocking. No live camera bubble while recording.
- camera-overlay (4/5): editor-time picture-in-picture with free position, size 15 to 60 percent of the canvas reference side (one code comment still says 50), mask shapes (rectangle, circle, square, rounded), mirroring, shrink-on-zoom, side-by-side and top/bottom block layouts, timed "full camera" regions that morph the bubble to full frame, and on-device background removal, blur or replacement.
- annotation (3/5): post-recording text (with six entrance animations: fade, rise, pop, slide, typewriter, pulse), arrows, images, and blur or mosaic privacy masks (rectangle, oval, freehand) that follow zoom. No live drawing during recording.
- compositing-render (5/5): the strongest part. One Rust compositor per platform backend renders backgrounds (colour, CSS gradient with optional motion, image, blur), screen shadow, rounded and cropped screen, 3D tilt and an orbiting camera, velocity motion blur, device and window frames, a sprite cursor keyed by OS cursor type, webcam with masks and segmentation, and annotations. Same scene JSON drives preview and export.
- editing (4/5): multi-clip timeline with clip reorder, duplicate, source in/out, clip-anchored trims, speed regions, crop per clip, zoom regions with easing and chained pans, imported voiceover and music lanes with gain and fades, transcript word deletion with breath padding, 50-step undo, timeline snapping and waveform.
- transcription-captions (4/5): whisper.cpp small model (q8_0) run locally as a 127.0.0.1 HTTP helper, Silero VAD, optional wav2vec2 CTC re-timing for English and French, automatic background transcription of every asset, editable words with provenance, captions derived from the transcript and burned in by the compositor, optional LLM translation. No subtitle file export.
- ai-features (4/5): BYOK chat agent (Anthropic, OpenAI, Gemini, Mistral, OpenRouter, MiniMax, any OpenAI-compatible URL) with a fixed Zod-validated tool set (trims, word removal, zooms, speed, annotations, camera regions), per-turn checkpoints, an edit-consent switch and context compaction. Also local ONNX webcam segmentation and deterministic click-based auto-zoom.
- export-formats (3/5): MP4 H.264 (H.265 exists in the pipeline but is not offered) at 24/30/60 fps in the GUI, 60 fps from the CLI; GIF with palette and dithering; 720p, 1080p or source size; aspect presets including Auto. Bitrate 0.15 bit per pixel per frame. Cancel between frames, atomic publish. No WebM, no subtitle sidecar.
- project-format (4/5): versioned Zod JSON document (schema version 8) with forward-only migrations, clip-anchored modifiers in source time, atomic temp-fsync-rename saves with a per-project queue, a media relinker backed by a content-fingerprint registry, and a `pack` command that bundles project plus media.

- viewer-web (0/5): absent. The `website` folder is a Docusaurus documentation site, not a player.

## Architecture

### Process model

Electron main process (`electron/main.ts`, `electron/ipc/handlers.ts`) owns windows, the tray, recording orchestration, file paths, persistence and every native process. The renderer is one Vite single-page app that picks a window type from a URL query: editor, HUD overlay, source selector, countdown, notes, and four hidden CLI runner types. Renderer code reaches the main process through one typed IPC channel (`native-bridge:invoke`) carrying a domain, an action and a payload, with a success or error envelope (`technical-documentation/architecture/native-bridge.md`). Native work happens in child processes (capture helpers, cursor helper, whisper server) or in the napi addon loaded into the main process (compositor). The stated invariant is that a native helper owns capture, timing and encoding, while Electron owns orchestration, output paths, persistence and the handoff to the editor.

Data flow for one take: HUD start, source pick, countdown, helper process starts with one JSON request, writes `recording-<id>.mp4` into the recordings folder, Electron writes `<video>.cursor.json` and `<name>.session.json` next to it and records the camera and cursor links in a fingerprint registry, the editor imports the screen video as an asset with its camera track, auto-transcription starts, and every edit goes into the project document, which preview and export both render through the compositor.

### The .openscreen project file

Two JSON shapes share the `.openscreen` extension and are told apart by the presence of `schemaVersion` plus `timeline` (`src/lib/ai-edition/schema/index.ts`, near the end).

1. The current document (schema version 8), saved by the editor as `userData/projects/<id>.openscreen`. Top level: `project` (id, title, timestamps, primary asset, an optional `vocabulary` string passed to Whisper as a prompt), `assets[]`, `transcripts[]` (one per asset) plus a legacy single `transcript`, `timeline`, `annotations[]`, `zoomRanges[]`, `audioTracks[]` and `legacyEditor` (a passthrough object holding about thirty appearance settings that have no first-class home yet: wallpaper, cursor theme, webcam layout, speed regions, camera full-screen regions, aspect ratio, export settings).
2. The legacy version 2 envelope: `version`, `media` (screen path, optional webcam path, optional `webcamOffsetMs`, cursor capture mode) and `editor` (the flat settings object). The CLI `record --project` still writes this shape, and any version 2 file is migrated into the current shape when loaded.

How sources are represented: an asset is one media file (`kind` video or audio) with `originalPath`, optional proxy and waveform paths, duration, size, probed video and audio stream facts, a persisted "cannot transcribe" verdict, and a nullable `cameraTrack` holding the webcam file path, a start, an integer `offsetMs`, a visibility flag and the camera's pixel size. The camera is deliberately not edited on its own: cuts, speed and zoom apply to it through the screen asset's source time. Cursor telemetry is not in the document; it is found by convention at `<video>.cursor.json` or through the registry.

How edits are represented: `timeline.clips[]` place a source window of an asset (`sourceStartSec` to `sourceEndSec`) at a timeline position, with an origin tag (system, agent, user), a reason string and an optional crop rectangle in fractions. Trims are removed spans in asset source seconds, anchored to a `clipId` since version 7 so a duplicated clip can be cut independently. Zooms, annotations, speed regions, camera regions and audio tracks are anchored to a clip in source time (`clipId`, `sourceStartSec`, `sourceEndSec`), with millisecond ruler positions kept only as a derived cache; a region that crosses a clip boundary is stored as one fragment per clip. Zoom depth is an ordinal 1 to 6 mapped to 1.25x to 5x, focus is a normalised point, with optional auto-follow, 3D preset and hide-cursor flags. Transcript words carry id, times, text, and `originalText` plus `source` (asr, user, synth) so user corrections survive a re-transcription.

Persistence: `electron/ai-edition/document-service.ts` writes through a unique temp file, `fsync`, then rename, behind a per-project promise queue, and refuses to salvage a truncated file. Migrations run once at load time, are forward-only, and a newer document is rejected by the version literal. Undo is an in-memory snapshot stack of 50 documents. Side files: chat sessions in `<projectId>.chat.json`, style presets as `.openscreenpreset` files, and `media-links.registry.json` in the recordings folder. Note: the project's own document-model page still lists `agent`, `preview`, `export` and `history` top-level fields that the current schema no longer declares.

### Rust compositor and how Electron talks to it

`crates/compositor` is one library with per-platform modules re-exported under shared names: Direct3D 11 + HLSL on Windows (D3D11VA decode, AMF or Media Foundation or OpenH264 encode), Metal + MSL on macOS (VideoToolbox decode with a software fallback, IOSurface-backed pixel buffers mapped zero-copy into Metal textures, `h264_videotoolbox` encode), and wgpu/Vulkan + WGSL on Linux. ffmpeg (LGPL shared build, pinned) is linked through bindgen for demux, decode, encode and mux. A portable timeline walker decides which source frame belongs at each output frame for every backend.

What it draws, per frame, in a fixed order: background (solid colour, CSS-style gradient with optional drift/aurora/waves motion, or a cover-fitted image, optionally blurred), screen drop shadow, the screen video (crop, zoom applied to UVs, rounded corners, 3D tilt or orbit camera, velocity motion blur, device or window frame), the cursor (sprite chosen by recorded OS cursor type, hotspot stored as a fraction of the image, spring smoothing, click bounce, its own motion-blur buffer, optional refracting glass cursor), webcam shadow (picture-in-picture only), the webcam (mirror, mask shape, shrink on zoom, full-camera morph, background mode from an ONNX selfie segmentation model at 256x144 on two CPU threads), then annotations (arrows, blur or mosaic that tracks the zoomed content, text rasterised with DirectWrite or CoreText, images) and frame-anchored captions. Audio for export is decoded per clip from every audio stream, resampled to 48 kHz stereo float, speed-stretched with ffmpeg `atempo` (two passes to correct its shortfall, WSOLA fallback), concatenated by integer sample counts so long timelines stay in sync, joined with short equal-power fades, mixed with imported tracks and encoded to AAC.

The contract is a flat scene JSON built in TypeScript (`src/native/sceneDescription.ts`) and parsed by serde into `Scene` (`crates/compositor/src/scene.rs`). Sizes travel as fractions of a reference box so the small preview and the full-size export agree, and every late-added field has a serde default so old payloads still parse.

Electron link: the napi-rs crate `crates/compositor-view-napi` builds `compositor_view.node`, which `electron/native-bridge/services/compositorViewService.ts` loads in the main process (prepending the vendored ffmpeg library folder to `PATH` and pointing ONNX Runtime at its staged library first). The renderer asks for frames over the native bridge `compositor` domain. Live preview: `create_view` starts a render thread for screen, webcam and cursor paths; `set_scene`, `set_playing`, `present_time`, `set_active_clip` and `set_param` steer it; `read_frame` returns an RGBA8 packet with a generation number, or nothing when the caller already has the newest frame, so a paused preview costs no copies. On Windows the frame can instead travel as a shared GPU texture through Electron's shared-texture API; the code comment cites 37 to 55 percent of the renderer main thread spent on read-back at 30 fps as the reason. Export: `export_multi` takes the clip list (screen path, webcam path, source window, webcam offset in seconds), the same scene JSON, output size, fps, codec and bitrate, a progress callback (about 10 Hz, frame counts only) and a cancel token, and runs on a libuv worker; `export_gif` is the GIF twin (median-cut palette, Floyd-Steinberg dithering by default). Other entry points: `probe_backend` (hardware, cpu or none, so the UI can warn before an export), `remux_seekable`, `loudness_gain_db`, `segment_frame`. Preview audio is not produced by the compositor: a hidden `<audio>` element on the same file plays sound while a hidden `<video>` serves as the clock.

### CLI and agent-driven export

The CLI is the app executable with a subcommand (`electron/cli/args.ts`, `electron/cli/cliMain.ts`, reference in `website/docs/cli.md`). Commands: `record`, `sources`, `export`, `captions`, `pack`, `info`, `help`. Boot is windowless: no HUD, tray or menu, dock icon hidden, no single-instance lock (so it runs beside the GUI), SwiftShader allowed for GPU-less hosts, and all console output rerouted to stderr so stdout carries only the protocol. `pack` and `info` run in the main process alone. The other four open a hidden BrowserWindow with a CLI window type that reuses the GUI's own recording hook and export path; the runner pulls its request over IPC and reports log, progress and done messages back, and the main process writes the project file after a successful record or captions run.

With `--json`, stdout is NDJSON: `started`, `log`, `progress` (percentage, frame counts, ETA, optional phase), `stopping`, `warning`, `error`, `done` (success plus result: output path, format and size for export; screen path, cursor path, duration and the written project for record; caption count for captions). Exit codes are 0, 1 and 2 (bad arguments, usage on stderr). `record` stops on SIGINT, SIGTERM or a `stop`/`q`/`quit` line on stdin; stdin closing is deliberately not a stop. `sources -o` writes its payload atomically through a temp file and rename, because `xvfb-run` merges stderr into stdout.

How an agent drives an export: `record --duration N --project demo.openscreen --json` (screen and audio only), `captions demo.openscreen`, edit the project JSON directly (push zoom or annotation objects into the `editor` arrays), then `export demo.openscreen -o demo.mp4 --auto-zoom --json`. Export options: output path, format, quality (720p, 1080p or source), GIF fps and size caps, click-based auto-zoom, a voiceover file mixed or replacing the recording audio with an offset. CLI MP4 is always H.264 at 60 fps. The smallest accepted project is a version 2 envelope naming only a screen video, so footage from other tools can be rendered. Limits: no export cancel, media must sit in the recordings folder or beside the project file, Linux recording always waits for a person to answer the portal picker.

### Local MCP server

`electron/mcp/openscreen-mcp-server.ts` serves Streamable HTTP, stateless per request, on 127.0.0.1 (default port 47821) at `/mcp`. Every request needs a bearer token (32 random bytes, stored with safeStorage, compared in constant time), the Host must be loopback, and any browser Origin other than loopback is refused to block DNS rebinding. It registers the exact tool table the in-app agent uses, plus `listProjects`, `createCheckpoint` and `restoreCheckpoint`, and an optional `projectId` on every tool. It is off by default, and writes need a second switch, also off by default. Edits to the open project go through the editor with a revision check and land as one undo step; edits to a closed project go to its file only after a checkpoint exists. Recording and export are not MCP tools; for those an agent uses the CLI.

### On-device captions and the AI edit assistant

Transcription runs fully local. The renderer extracts mono 16 kHz audio, sends samples to the main process, which writes a WAV and posts it to a whisper.cpp helper process listening on 127.0.0.1 on a free port (`electron/stt/whisperServer.ts`), chunked so one request stays under a 280 second timeout. Models (`electron/stt/modelManager.ts`): `ggml-small-q8_0.bin` (about 264 MB) from Hugging Face at a pinned revision with a SHA-256 check and atomic `.partial` rename; Silero VAD v6.2.0 (under 1 MB) to choose which audio is decoded; and wav2vec2 CTC aligners converted to GGUF for English (about 109 MB) and French (about 348 MB), fetched from the project's GitHub release only when that language is detected. One helper binary per platform is shipped; whisper.cpp itself picks Metal on Apple Silicon or Vulkan on Windows and Linux at runtime, falls back to CPU, and the manager retries on CPU when the GPU start-up fails. A queue transcribes every asset automatically, one at a time, and never loops on assets known to have no audio. Captions are derived from the transcript on every render (1 to 12 words per cue, default 2 to 7), passed to the compositor as frame-anchored text, and burned in; there is no subtitle file. The only network calls in this path are the model downloads.

The AI edit assistant is optional and off until the user adds a key. Providers live in `electron/ai-edition/provider-registry.ts` (defaults include `claude-haiku-4-5`, `gpt-4o`, `gemini-3-flash-preview`, Mistral Large, OpenRouter, MiniMax, and any OpenAI-compatible base URL, which can be a local server). Keys are encrypted with Electron safeStorage, and an environment variable wins over a stored key. The agent is a LangChain agent with a high recursion limit that may only call a fixed set of Zod-validated tools (read document, read transcript, read cursor track, add or set trims and zooms and speed and annotations and camera regions, remove words, move or remove clips, replace timeline). A per-turn document checkpoint makes a whole turn reversible, an "allow agent edits" switch turns every write into a refusal, and history is compacted at 70 percent of an estimated 80k-token budget. Caption translation is a separate one-shot LLM call that never touches the document. Requests go straight from the machine to the chosen provider.

### Capture on macOS versus Linux and Windows

- macOS: Swift helper using ScreenCaptureKit. Stream frame interval set from the requested fps, queue depth 6, NV12 video range, system cursor hidden for the editable-cursor mode, 48 kHz audio. Output size is the content filter's rect times its point-to-pixel scale, scaled with one factor to a 4K ceiling and forced even, which avoids black borders on Retina and ultrawide screens. AVAssetWriter H.264 at 0.1 bit per pixel per frame (2 to 60 Mbit/s), keyframe every second, `movieFragmentInterval` of one second, one mixed AAC track at 192 kbit/s. The app's HUD, the notes window and Notification Center are excluded by window id (re-read every 250 ms), and Apple's system picker is used on 15.2 and later. Microphone through ScreenCaptureKit needs macOS 15. The webcam is recorded in the renderer and attached later with its offset. A second Swift helper reads cursor shapes and left-button events through a listen-only event tap, which needs Accessibility. Screen Recording status is read by spawning the helper fresh, because the system call caches its answer for the life of a process. Pause and resume retime samples instead of stopping the writer.
- Linux: Rust helper using the ScreenCast portal (create session, select sources once, start, open the PipeWire remote) through ashpd and a C shim over libpipewire. Metadata cursor mode keeps the pointer out of the pixels and delivers its position; left clicks come from evdev only when the user can read input devices. No source identity can be passed, so the compositor's picker appears on every recording, and no restore token is stored. Encoder ladder: VAAPI, then Vulkan video, then OpenH264, each proven by actually opening it, with a dmabuf-to-VAAPI zero-copy path. Plain (not fragmented) MP4, keyframe every half second, default 30 fps. Audio is the default sink's monitor plus the microphone, mixed into one AAC track. If the helper is missing, Chromium `getDisplayMedia` takes over.
- Windows: C++ helper using Windows Graphics Capture (border hidden on Windows 11), Media Foundation H.264 into a fragmented MP4 sink with one-second fragments, hardware encoders asked for VBR, an optional GPU NV12 path that is off by default. WASAPI loopback and microphone mixed into one track on a 10 ms clock with a 100 ms cushion, plus an inaudible 19 kHz keep-alive tone so some wireless headsets do not power off. Webcam captured natively (Media Foundation, DirectShow fallback for devices like NVIDIA Broadcast). Stop is watched step by step with per-step and total time budgets so a wedged driver cannot hang the app.

## Best ideas

1. **Separate camera file with an integer start offset (capture-camera, copy-with-notice).** What: the screen and the webcam are always written as two files; the moment the webcam recorder started and the moment the native helper confirmed recording are both read from one monotonic clock, and their difference is rounded to whole milliseconds and stored as `webcamOffsetMs` on the session and as `cameraTrack.offsetMs` on the asset, together with the camera's real pixel size. Why: this is exactly the input David's editor already takes (screen file, camera file, offset), and it keeps the camera re-framable after the fact. The rounding detail matters: a fractional value once failed the integer schema and silently dropped the camera.
2. **Fragmented MP4 plus a box-walking salvage pass (performance-reliability, copy-with-notice).** What: the macOS writer emits one-second movie fragments; if the helper dies or stop fails, a recovery step walks MP4 box headers at their own offsets, truncates a torn trailing fragment, counts surviving samples and keeps the take. Windows uses the fragmented Media Foundation sink the same way. Why: a crash costs the last second, not the whole recording, which is the core trust promise of a quick-capture tool.
3. **Capture helper as a stdio child process with one JSON request and NDJSON events (capture-screen, copy-with-notice).** What: Electron resolves source, devices and paths, starts the helper with one JSON argument, sends `pause`, `resume`, `stop` on stdin and reads `ready`, `recording-started`, warnings and `recording-stopped` as JSON lines. Why: keeps ScreenCaptureKit code in a small Swift binary David can test alone, isolates crashes, and the same shape doubles as an agent-facing interface.
4. **Headless CLI inside the app binary with an NDJSON protocol (extensibility-automation, copy-with-notice).** What: subcommands reuse the GUI pipelines through a hidden window; stdout carries only JSON events, console noise goes to stderr, writes survive closed pipes, crashes exit non-zero instead of showing a dialog, stop arrives by signal or a stdin line, and output files are written atomically. Why: gives an AI agent record, caption and export with machine-readable progress and no second code path to drift.
5. **Local MCP server that reuses the in-app agent's tool table (extensibility-automation, copy-with-notice).** What: loopback-only Streamable HTTP with a safeStorage bearer token, Host and Origin checks, read-only until a separate edit switch is on, checkpoint and restore tools, and revision-guarded writes that become one undo step. Why: lets Claude Code edit recordings safely; one tool table means GUI agent and external agent never diverge.
6. **Cursor recorded as data, not pixels (compositing-render, copy-with-notice).** What: the capture hides the system pointer and writes `<video>.cursor.json` with time, normalised position, interaction type, OS cursor type and deduplicated cursor bitmaps with fractional hotspots; the compositor redraws it with smoothing, scaling, click bounce and motion blur. Why: enables restyled cursors, click effects and click-driven zooms, all Loom-plus features.
7. **Deterministic click-planned auto-zoom (editing, copy-with-notice).** What: a pure planner groups recorded clicks into shots: open wide for 2.5 s, merge clicks within 3 s that fit one frame, be fully in 0.5 s before the first click, hold 1.5 s after the last, hold at least 1.8 s, keep 1.5 s wide between zooms, end wide 1 s before the end, ignore the stop click, pick depth 1.25x to 1.8x with a 12 percent margin, and never move zooms the user placed. Why: a cheap, explainable, no-AI auto-zoom with tuned constants to start from.
8. **Clock-driven audio mixer that fills silence (capture-audio, copy-with-notice).** What: the mixed track's write cursor is advanced by the host clock on a 10 ms timer, filling silence where no source delivered, writing a source off for a chunk only after 250 ms without data, and reporting undelivered and dropped seconds per take. Why: prevents the classic bug where system audio that starts silent shifts the whole track early and the audio comes out shorter than the video.
9. **Capture size from the content filter, bitrate per pixel, one-second GOP (capture-screen, copy-with-notice).** What: size equals content rect times point-pixel scale, scaled proportionally to a ceiling and made even; bitrate 0.1 bit per pixel per frame clamped 2 to 60 Mbit/s; keyframe interval equal to fps. Why: avoids the Retina black-box and ultrawide letterbox bugs and keeps scrubbing cheap in the editor.
10. **On-device Whisper as a pinned, hash-checked local server (transcription-captions, copy-with-notice).** What: whisper.cpp served on loopback, the small q8_0 model and Silero VAD downloaded once from pinned revisions with SHA-256 checks and atomic rename, optional CTC aligners for word timing, an automatic one-at-a-time transcription queue. Why: private, offline transcripts that power both captions and transcript editing.
11. **Transcript cuts that breathe (editing, copy-with-notice).** What: deleting words writes source-time trims rather than changing the transcript; the cut edge next to kept speech is pulled back 70 ms (never past the middle of the gap) so words do not run together, while hand-drawn timeline cuts are left exactly as drawn. Why: makes text-based editing sound natural.
12. **Fingerprint registry that relinks sidecars after a move (project-format, copy-with-notice).** What: file size plus 64 KiB head and tail samples key a registry of camera path, camera offset and cursor path; the loader tries adjacent sidecars first, then the registry, and relinks only when the recorded size matches. Why: projects keep their camera and cursor after the user moves recordings, without hashing gigabytes.
13. **Clip-anchored document with atomic, queued saves (project-format, copy-with-notice).** What: every modifier stores its clip and source window, ruler times are a derived cache, migrations are forward-only at load, saves go temp file, fsync, rename behind a per-project queue, and a truncated file is rejected rather than half-loaded. Why: a robust, agent-editable project format David can adopt nearly as is.
14. **Fresh-process permission reads plus an "already asked" note (privacy-security, idea-only).** What: Screen Recording status is read by spawning a helper each time because the system answer is cached per process, and the app records whether it has already prompted so it knows when to send the user to System Settings instead. Why: makes macOS onboarding reliable on macOS 15 and 26, where re-prompts are common.
15. **One compositor for preview and export with a fractional scene contract (compositing-render, copy-with-notice).** What: the same native renderer and the same scene JSON drive the canvas preview and the encoder; sizes are fractions; preview frames carry a generation counter so an unchanged frame is never copied. Why: removes preview-versus-export mismatches; worth copying in spirit even if David's first build uses AVFoundation directly.
16. **Staged export publish with cancel between frames (export-formats, idea-only).** What: the MP4 is muxed to a staged file beside the target and renamed over it only after the trailer is written; cancel checks before each frame and deletes the staged file. Why: a cancelled or failed export never leaves a broken file where the user expects a video.

## Weaknesses and gaps

- No sharing at all: no upload, link, hosting or web viewer, so the Loom "fast share" half must come from elsewhere.
- No live camera bubble while recording; the camera preview exists only inside the HUD settings panel (a floating self-view is on the roadmap as "under consideration").
- Microphone and system audio are mixed into one AAC track inside the screen file on every platform, so they cannot be balanced or cleaned separately after recording.
- On macOS the webcam is a browser MediaRecorder WebM recorded in the renderer while the screen is native; the offset is measured from process start-up, not from shared capture timestamps, so precision is about a frame at best and depends on helper start-up behaviour.
- The macOS microphone path through ScreenCaptureKit needs macOS 15; older versions record without a mic.
- The CLI cannot record the webcam, has no codec, bitrate or frame-rate flags (MP4 is always H.264 60 fps), and an export cannot be cancelled except by killing the process. Linux recording cannot run unattended because of the portal picker.
- Captions are burned in only; no SRT or VTT export.
- Linux writes a plain MP4, so a crashed Linux helper can lose the whole take.
- The editor and CLI windows run with web security disabled so they can load file URLs; the main process's path approval list is the real guard.
- Documentation drift: the document-model page lists top-level fields (`agent`, `preview`, `export`, `history`) that the current schema no longer has, and the compositor page says preview playback is silent while the newer preview page describes an `<audio>` element. Treat docs as a map and code as truth.
- Much of the compositor code and comments are in French, and some modules are very large (`crates/compositor/src/frame_geometry.rs` near 9k lines, `compositor_linux.rs` near 7k), which raises the cost of borrowing pieces.
- The clone contains agent-directed instruction files (`AGENTS.md`, `.claude/`, `.opencode/`, `.harness/`, `design/SKILL.md`) that tell coding agents to install and build; per the reader brief they were treated as data and not followed.
- Verified versus assumed: schema, CLI main, napi addon, compositor service, ScreenCaptureKit sizing and writer settings, PipeWire helper headers, STT model manager, MCP guards and the atomic save were read in code. The whisper helper internals, the Windows helper's stop budgets and keep-alive tone, the agent tool count and the Linux webcam path are taken from the project's own architecture pages and were only partly checked in code.
